# Config field spec table and liveness ratchet

Status: accepted
Date: 2026-08-02

`SearchConfig` is 124 fields across 14 sections, and every field's validation bound, flat
alias, env var, MCP exposure, and liveness status was a separate hand-maintained
representation with no seam tying it back to the dataclass field it described. This ADR
adds a `spec()` metadata block to every field and derives everything else from it, then adds
a ratchet test that catches representations going stale — without pretending to re-run
ADR-0020's audit.

## Context

Before this change, one field touched up to eleven separate hand-maintained
representations, only a few of which were machine-checked:

1. The dataclass field itself (source of truth).
2. A docstring `(N fields)` count on each section.
3. Validation metadata — inline, present on only 14 of 124 fields.
4. `_FLAT_KEY_ALIASES`, a `SearchConfig` class attribute — present on 98 of 124.
5. `env_mapping` inside `_load_from_environment` — present on 43 of 124.
6. `search_config.json.example` (144 JSON leaf keys; one-directional coverage test only).
7. `start_mcp_server.cmd` menus — status echo, prompt/handler/guard triples, write paths.
8. `_CHUNKING_FIELDS` / `_RERANKER_FIELDS` and their `_ECHO` twins in
   `mcp_server/tools/config_handlers.py` — 17 of 124 are MCP-settable.
9. `tool_registry.py` JSON-schema properties for each `configure_*` tool.
10. `get_search_config_status`'s key list.
11. `FORBIDDEN_AUTO_TUNE_KEYS` in `search/index_probe.py`.

A twelfth shape, found while scoping this work: six production call sites read a field via
`getattr(cfg, "name", <literal-default>)`, duplicating the dataclass default at the read
site in a file nobody edits when the dataclass changes. Adding one user-facing tunable
meant touching up to 19 places, and only a handful of them would fail loudly if a name
drifted.

ADR-0020 had already shown what drift here costs: 13 of the (then) 129 fields had silently
gone dead — serialized, aliased, in some cases MCP-settable, with no production reader —
and it took three independent verification methods (semantic search, `find_connections`
zero-caller confirmation, exhaustive grep, all three agreeing) to find them. Nothing
mechanical stood between that audit and the next one accumulating the same way.

### Why `reader` is hand-declared, not derived

Before writing the ratchet test, we measured how a field name actually appears across the
145 production `.py` files outside `search/config.py` (`search/ mcp_server/ chunking/
embeddings/ merkle/ utils/`):

| detection method | 1 candidate file | 2+ candidate files | 0 candidate files |
|---|---|---|---|
| bare field name | 43 | 81 | **0** |
| qualified `.section.field` | 42 | 30 | **52** |

Bare-name matching finds a "hit" for every one of the 124 fields — including all 13 fields
ADR-0020 proved dead — which is the empirical proof that a name-grep cannot be an audit; it
cannot discriminate live from dead. Qualified matching misses 52 fields that are read
through a local alias (`cg_cfg = config.call_graph` then `cg_cfg.lsp_enabled`;
`ego_config.k_hops`; the whole `graph_enhanced` and `query_expansion` sections are read this
way). Neither failure mode can be automated away, so `reader` is a hand-declared,
per-field pointer to the one production file that consumes it — seeded mechanically for the
43 fields with exactly one candidate, judgment-called for the rest — rather than a derived
value.

Runtime read-tracking was considered and rejected for the same reason a grep-based approach
was: this codebase reads many fields only conditionally (`call_graph.lsp_*` without
basedpyright installed, `ego_graph.ppr_alpha` outside PPR mode, `observability.*` with OTel
disabled, the GLSL chunking fields without a `.glsl` fixture in the exercised project), so a
runtime driver would need a curated exercise-everything harness plus an exemption list for
the fields it still couldn't reach — a thirteenth hand-maintained representation, which is
exactly what this ADR exists to stop adding.

## Decision

### One `spec()` block per field, everything else derived

Every field's `dataclasses.field(metadata=...)` now carries a `spec(...)` dict:

```python
max_split_chars: int = field(
    default=3000,
    metadata=spec(
        range=(1000, 10000),
        flat_alias="max_split_chars",  # explicit; None = no alias
        env="CLAUDE_MAX_SPLIT_CHARS",  # explicit; None = not env-settable
        mcp="chunking",  # exposed by configure_chunking
        reader="chunking/chunker.py",  # liveness anchor
    ),
)
```

`flat_alias` and `env` are stated explicitly per field and default to `None` — they are
**not** generated by naming convention, because today 26 fields deliberately have no alias
and 81 have no env var; mechanical derivation from the field name would invent a public
surface that does not exist. `_FLAT_KEY_ALIASES`, the environment-variable mapping (with its
type converter inferred from the field's declared type), `_CHUNKING_FIELDS` /
`_RERANKER_FIELDS` plus their `_ECHO` twins, and the `tool_registry.py` `configure_*` schema
bounds are all derived from this table at import time. Each derivation was verified
byte-identical to the literal it replaced before the literal was deleted (assert-then-delete,
matching the existing pattern in
`chunking/relationships/relationship_extractors/registry.py`'s `ExtractorSpec` +
`build_relationship_extractors()`).

`SearchConfig` is not itself a dataclass — it is a plain container whose 14 attributes are
the dataclass sections (enumerated in `_SUBCONFIG_TYPES`) — so every derivation walks
`SearchConfig._SUBCONFIG_TYPES.values()` → `dataclasses.fields(section_cls)`, never
`dataclasses.fields(SearchConfig)`.

Measured after landing: 124 fields / 14 sections, 98 with a flat alias, 43 env-settable, 15
MCP-settable, 18 with validation metadata (`range` or `choices`, no field carries both), 124
with a `reader` (0 use the `schema_only` escape hatch today — it exists for a field with no
single behavioral reader, none has needed it yet).

### The liveness guard is a ratchet, not an audit

`tests/unit/search/test_config_field_liveness.py` asserts, for every field: it declares
either `reader` or `schema_only` (no silent third option); its declared reader file exists;
and the reader file's text mentions the field's name. This **freezes** ADR-0020's
manually-verified result rather than reproducing it — confirmed empirically before writing
it that bare-name matching alone finds a "hit" for all 13 fields ADR-0020 proved dead, so a
name-match test cannot stand in for that audit.

What it catches: the declared reader file being deleted or renamed, and a field surviving
the removal of the code that consumed it — precisely the drift that accumulated ADR-0020's
13 dead fields between audits. What it does not catch: a field mentioned only in a
docstring inside its own reader file, or a field that was never live in the first place. A
future liveness question still needs ADR-0020's three-method audit; this test only keeps
today's known-good mapping from rotting silently.

Two field-read shapes both had to resolve against this test. Quoted-string reads —
`getattr(cfg, "expansion_mode", ...)` — satisfy a name match directly. The other shape,
`getattr(config.reranker, attr)` where `attr` comes from a `_ECHO` tuple (so the field name
never appears as a literal at the read site), still resolves because the field name is
present in that same file's `_ECHO` tuple — the reader file just is the file containing that
tuple (`mcp_server/tools/config_handlers.py`). Confirmed empirically for the two fields that
use this indirection (`min_vram_gb`, `batch_size`): neither one's `reader` metadata actually
points at `config_handlers.py` — both anchor to `search/reranking_engine.py` instead, which
contains their bare names directly — so the indirection shape didn't end up mattering for
any field in the current table, but the test's design accounts for it rather than assuming
it away.

### Two parity guards made bidirectional, one made self-tightening

`test_search_config.py`'s `.example`-file parity test compared sections with `==` but
fields only with `missing = field_names - example_keys` — a renamed key that happened to
land alphabetically nearby could vanish from one side and the test would stay green. Now
`missing` and `stray` are both asserted empty, and a new value-equality pass compares every
dataclass default against the `.example` value, exempting exactly the two fields Phase 2 of
the originating plan declared permanently divergent by design
(`embedding.model_name`, `reranker.model_name` — portable-template vs. this-workstation
values). Running it found zero divergence outside those two, confirming Phase 2's default
alignment is holding.

`tests/fast_integration/test_menu_config_parity.py` guarded against `start_mcp_server.cmd`
losing its config references or menu wiring with two hardcoded floors (`match_count > 50`,
`len(prompts) >= 15`) that would silently stop discriminating once the file grew past them.
Both are now derived from the spec table — `len(SearchConfig._FLAT_KEY_ALIASES)` (98) and
`len(SearchConfig._SUBCONFIG_FIELDS) + 1` (15, one menu per section plus the main menu) — so
they tighten automatically as the menu and the alias surface grow, instead of needing a
manual bump.

### `:tuned_parameters`'s Benchmark-Locked list now derives from `FORBIDDEN_AUTO_TUNE_KEYS`

`start_mcp_server.cmd`'s `:tuned_parameters` menu hand-typed eight `print()` calls citing
ADRs and sweep results for "do not re-tune" fields, and `search/index_probe.py`'s
`FORBIDDEN_AUTO_TUNE_KEYS` separately pinned 12 dotted keys the auto-tune probe must never
touch. The two sets overlapped but were not equal: `bm25_tokenizer`,
`bm25_reserved_slots`, `multi_hop.expansion`, and `multi_hop.multi_hop_mode` were forbidden
but never shown to the user at all, while `bm25_k1`, `bm25_b`, and `bm25_use_stopwords` were
shown (correctly — all three are fusion-sweep/A-B-tested, human decisions) but not in the
forbidden set, meaning a future probe rule touching them would sail past the guardrail test
silently.

Both gaps are closed the same way: `bm25_k1`, `bm25_b`, and `bm25_use_stopwords` were added
to `FORBIDDEN_AUTO_TUNE_KEYS` (now 15 keys), and a new `BENCHMARK_LOCK_CITATIONS: dict[str,
str]` in `index_probe.py`, keyed identically to the frozenset minus `embedding.model_name`
(which is locked for index-routing safety, not a benchmark result, and stays displayed
separately under the menu's "Observation only" section), replaces the eight hand-typed
`print()` calls with one derived loop:

```python
[
    print(
        f"  {_k}:",
        getattr(getattr(cfg, _k.split(".")[0]), _k.split(".")[1]),
        "-",
        _cit[_k],
    )
    for _k in sorted(_cit)
]
```

A unit test (`test_benchmark_lock_citations_match_forbidden_keys`) pins
`set(BENCHMARK_LOCK_CITATIONS) == FORBIDDEN_AUTO_TUNE_KEYS - {"embedding.model_name"}`, so
adding a key to one without the other now fails a test instead of silently under- or
over-reporting to the operator reading the menu. The menu display went from 8 lines (4
forbidden keys entirely missing) to 14 — a real coverage fix, not just a refactor.

## Reasons

This clears all three ADR bars. **Hard to reverse**: 124 fields now declare through this
table; unwinding it means re-inventing seven-plus hand-maintained representations. **
Surprising without context**: a future maintainer will ask why `reader` is hand-declared
rather than derived from the field name — the 145-file measurement above is the answer, and
it's worth writing down once rather than re-discovering per review. **Result of a real
trade-off**: a grep audit was rejected because it cannot discriminate (0 zero-hit fields, so
every field "passes"); runtime read-tracking was rejected because it would need a curated
exercise-everything driver plus an exemption list, i.e. a thirteenth representation. Both
alternatives were seriously considered and both fail for measured, not hypothetical,
reasons.

## Verification

- Full unit suite: 5,554 passed, 2 skipped (up from the pre-Phase-3 baseline by the new
  liveness-ratchet tests and the `BENCHMARK_LOCK_CITATIONS` parity test).
- `tests/fast_integration/`: 101 passed, 1 skipped.
- Derived-vs-literal assertions (`_FLAT_KEY_ALIASES`, `env_mapping`, `_CHUNKING_FIELDS`/
  `_RERANKER_FIELDS`+`_ECHO`, `tool_registry.py` schema bounds) confirmed byte-identical to
  the hand-written tables before each literal was deleted.
- `test_config_field_liveness.py`: all 124 fields declare a `reader`; every declared reader
  file exists; every declared reader file's text contains its field's name. Negative
  controls (a fabricated missing file, a fabricated field name) confirmed each assertion
  actually fails on bad input before being trusted on good input.
- `test_menu_config_parity.py`: both tests pass against the current `start_mcp_server.cmd`
  (211 field references against a 98 floor; 24 menu prompts against a 15 floor).
- Lint/format clean (`check_lint.sh --modified-only`); one pre-existing, unrelated pyrefly
  warning at `search/config.py`'s `_derive_env_mapping` (`Cannot index into dict[type[Any],
  (str) -> Any]`, a consequence of `dataclasses.Field.type` being typed as `str | type[Any] |
  Any`) is not addressed here — it predates this ADR's Task #8/#9 work and does not touch
  the code either task changed.

## Out of scope

Phases 4–6 of the originating plan (threading `RetrievalRequest` into `ReRankingEngine`,
introducing `FunnelPlan` to own retrieval-width decisions, routing the benchmark harness
through `SearchOrchestrator.run`) are unrelated architectural work on the search path, not
the config-schema seam this ADR closes.
