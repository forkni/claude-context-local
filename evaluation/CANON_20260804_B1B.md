# SSCG canon re-pin + `canon_B1b` intent-on arm — 2026-08-04

Re-pins the published canon to `canon_f1` (supersedes `canon_e1`) and captures `canon_B1b`, the
intent-on arm ADR-0023 gated `P4` (`reranker-config-required`), `A` (`funnel-plan`), and `B2` behind.
Both are captured on the same substrate: **204 files, 2324 chunks** (`cleanup_resources` +
`tools/batch_index.py --path . --mode force`, 38.73s), `audit_golden_dataset.py` CLEAN on both
datasets (77q/147q) against that index, `PYTHONHASHSEED=0` (ADR-0021) + `CLAUDE_AUTO_REINDEX=0` for
every capture.

## What changed, and why a re-pin was required

The five commits landing in this round (`e7d623a` parallel-edge-collapse, `cfe83a0`
mcp-field-derivation, `dff0ed7` project-activation-pairing, `4177d8a` config-locator-inline,
`f4915c2` B1b harness instrumentation) are all off the SSCG scoring path — none touch fusion,
reranking, graph expansion, or scoring logic — but all edit indexed source, and per the project's
substrate-drift rule any commit that shifts the corpus invalidates the canon. `canon_f1` supersedes
`canon_e1` (`evaluation/CANON_20260804_ARM_OVERRIDES.md`, mrr 0.8363/0.8362 63q, 0.6803 133q).

**Single round per view**, extending `canon_e1`'s precedent: the 63q pair is the determinism control
and came back byte-identical (0 flips), so a second round of any other view on the same substrate
would confirm nothing new for ~25 min of GPU each.

## Root cause: two extractor bugs, not a threshold that needs tuning

- `_extract_symbol_from_query` (`search/intent_classifier.py:618-677`) — all three passes iterate
  `reversed(words)` over whitespace-split tokens, so a dotted symbol like
  `InheritanceExtractor._extract_from_tree` matches none of the three whole-word regexes and the
  scan falls through to a trailing prose word. Observed live in the arm log: that query extracted
  `hook`; a `PythonChunker.__init__` query extracted `codebase`. Q71's redirect returned
  `LanguageChunker.extract_metadata`, `CppChunker.extract_metadata`, `TypeScriptChunker._extra_metadata`
  — unrelated to its golds.
- `_extract_path_endpoints` — regex-matches ordinary prose. Q72, *"strip line range **from**
  chunk_id **to get** stable normalized identifier"*, yields `source='chunk_id', target='get'` at
  confidence 0.86. `find_path` redirects carry `fallback_on_error=False`
  (`search_orchestrator.py:166-177`), so Q72's `retrieved` was `[]` — no results at all.

**No config-only lever exists.** Misfire confidences are 0.78–0.93 against a 0.4 gate, so raising
`intent.confidence_threshold` cannot separate good redirects from bad; worse,
`intent_classifier.py:273` demotes sub-threshold queries to `default_intent`, so raising it collapses
*every* query to HYBRID and takes the (inert) adaptive machinery with it. `IntentConfig`
(`search/config.py:543-586`) has six fields and none isolates redirects. Only lines 168 and 183 of
`search_orchestrator.py` gate on the threshold; the ego/edge-weight branches are ungated.

The 9 `find_similar` redirect queries in the 63q arm are **exactly** the 9 anchored F queries, so
the same queries are measured three ways on this substrate:

**The realistic repaired ceiling is not 0.8519.** Q70, Q71, Q96, Q99 carry
`similar_exclude_same_file=True` in the golden dataset (4 occurrences per dataset file) — hand-
authored caller intent the redirect cannot see. A static exclusion policy was already measured and
**failed** (commit `402b1d0` — rescues Q71, zeroes Q97, whose golds are all same-file). Backing that
benefit out puts a repaired redirect near **0.54–0.61** against the normal path's 0.4577: a real
**+0.09 to +0.15** on these 9 queries, ≈ **+0.012 to +0.021** on the 63q aggregate.

`recall@20` runs the other way: 0.7966 normal vs 0.7185 even in the annotated F-view. `find_similar`
buys head precision by returning a far smaller pool (3.1 vs 29.5) — any gate on a repair must price
recall, not just MRR.

**`find_path` has no upside evidence at all.** Both instances across both datasets (Q72, Q121) are
prose misfires; no query in either golden set would be helped by repairing `_extract_path_endpoints`,
so a successful "fix" could only mean *stopped firing* — which removal also achieves, without
retaining a branch whose failure mode is an empty result set.

## Disposition (decided)

**Keep** everything else in `SearchConfig` as-is; nothing outside the intent layer moved.

1. **Stopgap (Round B):** flip `intent.enabled` to default `False`
   (`search/config.py:546`), and remove the `find_path` redirect entirely
   (`search_orchestrator.py:166-177` + its extractor + its tests). Stops the live failure —
   including the empty-result class — immediately. **Already mitigated locally** via
   `<repo>/search_config.json` (`intent.enabled: false`, gitignored runtime override,
   `CONFIG_PATH_CANDIDATES[0]`); the source default is what Round B changes.
2. **Repair and re-measure (Round C):** fix `_extract_symbol_from_query` by reusing
   `_detect_code_symbols`'s existing tokenization (`re.findall(r"[\w.]+", …)`) and predicate set
   (`is_camelcase`/`is_upper_const`/`is_snake_or_dunder`/`is_dotted_symbol`, already imported), then
   re-run the intent-on arm against a same-substrate intent-off control and judge it against a
   pre-registered gate.
3. **If the gate fails, remove the mechanism altogether** — the similarity redirect goes too,
   leaving classification + QW5 + A1, all measured inert, making the whole intent layer a removal
   candidate on the ADR-0015/ADR-0016 precedent.

**Pre-registered gate** for Round C, on the 9 similarity queries, replicated on 63q **and** 133q:

> MRR must **exceed** the same-substrate normal-path mean, **and** recall@20 must **not** fall below
> the same-substrate normal-path mean by more than run noise.

Both baselines must be re-derived on the repair round's own substrate — the 0.4577/0.7966 figures
above belong to *this* substrate and the drift rule forbids reusing them across a commit.

## Two known instrument limits (recorded, not fixed)

- `_extract_suggested_params` hardcodes `params["k"] = 10` for GLOBAL
  (`search/intent_classifier.py:573-576`) and the orchestrator bumps only when `suggested_k > k`
  (`search_orchestrator.py:150-160`). At the canonical `k=10` that branch cannot fire, while
  production (`default_k=7`) does exercise it. `canon_B1b` therefore measures the intent layer
  minus the k-bump.
- The `search_mode` suggestion branch is dead in the harness: it requires `AUTO`, and the harness
  always passes a concrete `"hybrid"`.

## Comparability

- **`canon_f1` supersedes `canon_e1`** as the published baseline (63q and 133q views). `canon_B1b`
  is a named arm, not a published canon — the production canon stays intent-off per ADR-0023's own
  rationale (redirects scoring differently would silently redefine what the headline MRR measures).
- **`canon_B1b`'s figures belong to this substrate only.** Round B/C re-measurements must re-derive
  their own control, not diff against these numbers directly.
- Capture JSONs (`evaluation/sscg_canon_{f1,B1b}_*.json`) are **not tracked in git**, per the
  precedent set by every prior canon capture — this markdown file is the durable record.
