# jina-reranker-v3.5 vs v3 A/B — 2026-08-14

## Verdict: REJECTED — `reranker.model_name` stays `jinaai/jina-reranker-v3` (local default, unchanged)

v3.5 is decisively **not non-inferior** on this project's code corpus. All four gated
splits (63q train/val, 133q train/val) have an MRR paired 95% CI lower bound below the
−0.02 threshold — two of them (63q val, 133q val) by an order of magnitude:

| split | n | mean ΔMRR | 95% CI | gate |
|---|---|---|---|---|
| 63q train | 35 | −0.0452 | [−0.1071, +0.0166] | **FAIL** |
| 63q val | 13 | −0.0385 | [−0.1441, +0.0672] | **FAIL** |
| 133q train | 78 | −0.0100 | [−0.0534, +0.0334] | **FAIL** |
| 133q val | 25 | −0.1200 | [−0.2430, +0.0030] | **FAIL** |

The latency half of the gate passes cleanly — v3.5 is ~43% faster (median) on every
view, and determinism holds (0 moved queries, 63q repeat) — but the gate is an AND, and
quality fails first. `search_config.json` is unchanged (already on v3 — verified, never
touched by this trial). Phase 1 code (version-aware `rerank()` length-kwargs resolution)
stays committed as a standalone correctness fix — see "What stays from this work."

## Pre-registered gate (written before any Phase 2 run)

**Adopt `jinaai/jina-reranker-v3.5` as the local `reranker.model_name` iff, on the train
and val splits of BOTH the 63q canonical golden set AND the 133q expanded golden set,
MRR paired 95% CI lower bound > −0.02, AND median rerank latency improves** (v3.5 median
`per_query[].latency_ms` < v3 median, computed post-hoc from the same captures).

Any MRR CI whose lower bound falls at or below −0.02 on either dataset (train or val) →
reject and stop; no partial adoption. This is the user-selected "non-inferior + faster"
gate (see plan `i-ve-discovered-that-jina-v3-5-sleepy-mist.md`), stricter than methodology
rule 7's "excludes zero" default — chosen because v3.5 publishes no code-retrieval (CoIR)
number, only NL/multilingual/structured benchmarks (BEIR/MIRACL/RTEB/Struct-IR), so
non-inferiority on our own code corpus is the bar, not superiority.

## Motivation

Jina released `jina-reranker-v3.5` (arXiv 2607.18152), a same-size (596.8M, Qwen3-0.6B
backbone) successor to the deployed `jinaai/jina-reranker-v3`. Feasibility and Phase 1
code support (version-aware `rerank()` length-kwargs resolution — v3.5 dropped
`max_doc_length`/`max_query_length`, hardcoding 8192/1024 internally, which is a
`TypeError` on a naive config-only swap) are covered by the approved plan and landed in
commit (pending — see Status). This document covers Phase 2 (A/B) and Phase 3
(disposition).

## Protocol

6 runs (3 views x 2 arms), interleaved control/treatment within each view, plus 1
determinism repeat:

| View | Flags | Purpose |
|---|---|---|
| 63q full | *(defaults)* | canon-comparable headline + per-split gate evidence |
| 133q full | `--golden-dataset evaluation/golden_dataset_expanded.json` | canon-comparable headline + per-split gate evidence |
| F-via-similar | `--f-via-similar` | similarity view |

Train/val paired CI computed post-hoc via `--compare-split train` / `--compare-split val`
from the full-set captures (each `per_query` record already carries `split`) — no
separate `--split` runs needed. `aggregate_by_slice.py` run per capture for per-split
context; `recall@20`, `pool_hit_rate`, `peak_vram_reserved_gb` recorded per arm as the
Risk 7 (sliding-window cross-doc attention) / Risk 4 (VRAM) diagnostic signature.

## Reading

- **Quality loss is broad, not a single mechanism.** The plan's Risk 7 hypothesized a
  clean signature — MRR flat while `recall@20`/`pool_hit_rate` drop — if the sliding
  window (1024 tokens, ~20/28 layers local) were purely attenuating cross-document
  comparison inside an otherwise-adequate candidate pool. That signature is *partially*
  present (`recall@20` and `pool_hit_rate` both drop alongside MRR on 63q/133q), but MRR
  itself drops hard and inconsistently across categories — category F (similarity) is
  perfectly tied, C (class_overview) is slightly *better*, while A (small_function) and B
  (sibling) — the two categories where the correct answer is one of several
  near-identical candidates — lose the most (−0.078, −0.083). That pattern reads as
  degraded fine-grained discrimination among close candidates, consistent with (but not
  proof of) the sliding-window mechanism, rather than a pool-flooding or retrieval-recall
  problem upstream of reranking.
- **133q val is the single worst cell** (CI [−0.2430, +0.0030], 5/25 moved, two full
  rank-1-to-miss flips: Q102, H048) and pulls the aggregate down disproportionately
  relative to its size — but 63q train and val already fail on their own with much
  larger n, so this isn't a small-sample artifact carrying the verdict.
- **The latency win is real and large** (~43% median, holds across all three views,
  survives on sdpa with no flash-attn) — if a future retrial changes the quality
  picture, the speed case does not need to be re-litigated.
- **VRAM headroom is not a concern either way**: v3.5 peaks ~0.5-0.8GB higher than v3
  (14.2-16.3GB vs 13.5-15.9GB), both far under the 24GB card's ADR-0011 cliff region
  (27.66GB reserved was the v3 cap-4000 pathological case).

## What stays from this work

Phase 1 code stays (commits `2ca05f9`'s incidental 3-hunk absorption in
`search/config.py` + `a245c79`): the version-aware `rerank()` length-kwargs resolution
is a standalone correctness fix independent of this verdict — it makes `create_reranker`
tolerant of a `rerank()` signature that omits `max_doc_length`/`max_query_length` (which
v3.5 does, hardcoding 8192/1024 internally) instead of hitting a `TypeError`, and hardens
the existing v3 path against any future upstream signature drift (Jina republishes
`modeling.py` in place). `jinaai/jina-reranker-v3.5` also stays selectable in
`RERANKER_SWEEP`, the installer menu, and `configure_reranking`'s schema — useful for any
future retrial without further code changes. `search_config.json` (local, gitignored)
stays on `jinaai/jina-reranker-v3`, untouched throughout this trial (verified).

## Reopening condition

Do not re-propose `jina-reranker-v3.5` on point estimates or published aggregate
benchmarks (BEIR/MIRACL/RTEB/Struct-IR) alone — those already existed pre-trial and were
explicitly not trusted as evidence for code retrieval (see Motivation / plan Risk 1).
Reopen only if one of the following changes:

1. **A newer Jina listwise checkpoint** (v3.6+, or a v3.5 point release) ships with a
   corrected or widened sliding-window configuration — re-run this same protocol fresh,
   don't reuse these numbers as the new baseline's control.
2. **The `listwise_doc_max_chars` cap is revisited downward** as its own independent A/B
   (ADR-0011 is scoped to v3; a smaller cap could pack more of the candidate set inside
   v3.5's 1024-token local-attention window per Risk 7's mechanism) — if that trial ships
   a materially smaller cap as the new default, re-run the v3.5 A/B against the new
   substrate; a few points of MRR recovery from a smaller cap would not by itself close
   a gap this large (63q train/val alone need +0.045-0.14).
3. **A different Jina v3.5 hyperparameter is found to matter** (e.g. dtype interaction,
   `top_n` truncation behavior) — no such lever was found or tested in this trial; this
   is a placeholder for future investigation, not a lead currently in hand.
